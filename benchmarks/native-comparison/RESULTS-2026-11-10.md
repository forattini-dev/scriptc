# Native comparison results — 2026-11-10

This checkpoint compares Node.js 26.12.1, Bun 1.4.4, and scriptc native `0.1.1-rust.0` with rustc 1.99.1 on Windows. Builds and executions were serialized. scriptc used one Cargo job, the Rust frontend and backend, and no JavaScript engine or fallback.

Node's standalone lane uses the built-in [single executable application builder](https://nodejs.org/api/single-executable-applications.html#generating-single-executable-applications-with-build-sea) with V8 code cache enabled. TypeScript is stripped by Node's `node:module` API before SEA generation. Bun uses `bun build --compile`. These executables embed their respective JavaScript runtimes; scriptc emits a Rust application, so their sizes describe different deployment models.

Every reported execution matched Node source byte-for-byte on stdout and stderr and returned the same exit code. Each runtime value is the median of three fresh processes after one warmup execution. CPU and peak private memory cover the complete process tree through a Windows Job Object. Windows accounts CPU in coarse ticks, so very short Bun runs can appear as zero CPU milliseconds even though their wall time is nonzero.

## Conclusions

The correctness result is strong but narrow: all three portable programs compile and preserve output in both default and optimized scriptc modes. It is not evidence that arbitrary Node or Bun applications compile.

scriptc already wins executable size by a large margin: 1.67–7.28 MiB versus 100.58 MiB for Node SEA and 109.93 MiB for Bun. It also uses substantially less runtime private memory in these workloads: about 6–18 MiB versus 26–41 MiB for Node and about 74 MiB for Bun.

Numeric code is competitive even in the default profile. Object/string traversal and native `Map`/`Set` remain the performance gap. `-O3` cuts records runtime by about 55% and collections by about 63%, but the optimized scriptc binary is still slower than Bun and is slower than Node for those workloads.

The next performance milestone should therefore be an official production profile rather than an environment-variable experiment. It needs a separately cached or prebuilt optimized runtime, repeatable warm/cold build measurements, and targeted profiling of record property access plus `Map`/`Set` hashing and allocation. That work should preserve the current low-memory and small-binary advantages.

## Follow-up: ordered hash index — 2026-11-11

The collection representation now retains its insertion-order `Vec` and adds an internal hash-to-slot index for string, number, boolean and erased primitive keys. Candidate slots are still checked with JavaScript equality, `NaN` is canonicalized, `-0` and `0` share a key, deletion invalidates shifted slots, and unsupported key representations retain the linear fallback. This remains native Rust without an engine or fallback.

A new differential test covers updates without size growth, deletion and reinsertion, duplicate set insertion, missing keys, `NaN`, and `-0`/`0`. The focused collection gates passed: seven Map-filtered tests, the flow-selected Set test, stateful Set iteration, WeakSet boundaries, and the new semantic test.

## Follow-up: proven typed record slots — 2026-11-11

Bun's experimental AOT compiler documents three property-access tiers: a known shape is one fixed-offset load, a partially known shape adds a guard, and an unknown object performs a name lookup. Its current implementation retains declaration-order fields while building a separate key index, propagates layouts through assignability checks, keeps numeric and boolean slots unboxed where their declared type permits it, and falls back when an object's shape cannot be proved. Relevant upstream references are Bun's [AOT overview](https://bun.com/docs/compiler/aot), [slow-path report](https://bun.com/docs/compiler/explain), [`OwnFields`](https://github.com/oven-sh/bun/blob/2596ac5d391d47804c93a42bdbe615804aa62387/src/aot/lower/layouts/own_fields.rs), and [`literal_slots`](https://github.com/oven-sh/bun/blob/2596ac5d391d47804c93a42bdbe615804aa62387/src/aot/link/literal_slots.rs).

scriptc now applies the same general principle through its own IR and Rust representation. A closed record is eligible only when every field has a non-optional scalar type and the module contains no structural view, checked erased-object conversion, computed property access, own-property reconstruction, callable layout, tuple or index signature that requires shared dynamic storage. Eligible records emit Rust structs with typed `bool`, `f64`, `JsString` or `JsBigInt` slots. Every other record retains the identity-preserving `NativeRecordData` store. This avoids changing the representation of the dynamic and structurally aliased cases merely to improve a benchmark.

The seven-run release benchmark preserved exact output parity in all 15 runtime modes:

| Records | 96.9 | 55.4 | 28.2 | 54.8 | 15.71 | 1.51 |
| Collections | 101.5 | 60.8 | 37.4 | 127.3 | 6.22 | 1.49 |

The typed-record workload improved from 109.9 ms to 54.8 ms, a 50.1% reduction. It now matches Node SEA within the measurement noise while using about 45% less private memory and a binary about 97% smaller. It remains approximately 1.94× slower than Bun's AOT executable, so further work should target allocations and string construction rather than reintroducing property hashing into known shapes.

The same specialization cut the records executable from 4.29 MiB to 1.51 MiB, warm compilation from 12.2 seconds to 6.6 seconds, and compiler peak private memory from about 353 MiB to 321 MiB because the generated program no longer retains the large erased-record adapter path for this workload.
