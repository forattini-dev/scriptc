# Sincronizar integralmente o upstream vercel-labs no fork Rust-first

## Objetivo

Trazer **tudo** o que a `vercel-labs/scriptc` produziu desde o ponto de fork para dentro do fork — os 88 commits (v0.1.2 → v0.1.4), o trabalho pesado de C/LLVM, a superfície Node estática, o corpus de testes e o Test262 — preservando a lane Rust como backend primário e sem regressão no differential Rust nem nos snapshots de diagnóstico. O upstream é onde o projeto está ganhando massa (C/LLVM, corpus, Test262) e ignorá-lo ficou caro: o fork está 88 commits e três releases atrás.

A integração é por **merge integral de `upstream/main`**, não por cherry-pick seletivo. Corpus, testes e infraestrutura entram inteiros; as ondas de linguagem e de superfície Node deixam de ser adoção item a item porque já chegam no merge. O trabalho muda de "escolher o que portar" para "resolver conflitos preservando a lane Rust e validar o resultado".

## Restrições e decisões já tomadas

- Rust continua o backend primário do produto; **C e LLVM deixam de ser congelados** e passam a ser mantidos atualizados pelo merge, porque o upstream investe neles e o corpus differential é backend-agnóstico.
- Merge **não-destrutivo**: nunca rebase, reset ou force-push sobre o trabalho dos 1114 commits do fork. Conflito se resolve no merge, preservando a lane Rust.
- Corpus é differential contra Node/Bun: stdout, stderr e exit code byte a byte.
- Não usar engine para esconder limitação (`--allow-engine:false` continua o alvo dos estudos nativos) e não alterar consumidores (Redcode) para mascarar o compilador.
- Checkpoint antes de cada passo: `git fetch origin && git merge --ff-only origin/main`.
- Sem documentação nova além deste arquivo; medições vão em `.red/researches/` como JSON.
- `pnpm` é o gerenciador padrão; em worktree com `node_modules` symlinkado, usar `node`/`npx` direto para não mutar deps compartilhadas.

## Estratégia de integração integral (merge)

1. **Descoberta de conflitos**: a partir de `main`, rodar um merge de ensaio (branch descartável ou `git merge-tree $(git merge-base main upstream/main) main upstream/main`) e produzir o inventário de caminhos conflitantes, cruzando com nossos commits. Não é para resolver ainda.
2. **Merge integral**: `git merge upstream/main` (ou `merge/upstream-20260925`) e resolver conflito preservando a lane Rust. Preferência de política: adotar a **estrutura** do upstream nos arquivos que ele refatorou (`#324`/`#325`) e reaplicar nossos deltas Rust em cima, para manter o fork mergeável nas próximas sincronizações; se o custo for proibitivo num arquivo, manter nossa estrutura e portar a mudança funcional do upstream, documentando a exceção.
3. **Validação por lane**: `pnpm -r build`; differential Rust (plain e `SCRIPTC_SAN=1`); snapshots de diagnóstico; corpus/corpus novo; C/LLVM onde o host permitir (o host não tem `llvm-config`/`lld`, então o LLVM local tende a SC3005 — registrar como limitação de host, não regressão).
4. **Baseline antes/depois** registrado no commit e em `.red/researches/` (JSON): corpus differential Rust (X/Y), contagem de diagnostics do Redcode no-pins, estado dos gates.
5. **Cadência**: depois do primeiro merge, sincronizar a cada release do upstream (v0.1.5+) via `merge/upstream-<data>`, usando `pnpm upstream:drift` como painel.

## Incrementos ordenados

1. **Descoberta de conflitos do merge**: inventário completo de caminhos conflitantes via `merge-tree`, com o commit nosso e o do upstream de cada lado. Verificação: lista cobre todo caminho conflitante e nenhum merge é aplicado.
2. **Merge integral do upstream/main + resolução preservando Rust**: merge dos 88 commits e resolução dos conflitos, com a lane Rust compilando. Verificação: `pnpm -r build` passa e um differential Rust focado passa.
3. **Corpus, Test262 e CI shardado**: aterrissar todo o corpus/testes do upstream, registrar a baseline de `expectations.json` da lane Rust e ligar o sharding de CI (corpus em seis shards, Test262 nos shards). Verificação: harness roda e reporta contagens; corpus novo passa; gates existentes continuam verdes.
4. **Reconciliação da lane Rust pós-merge**: restaurar differential Rust e snapshots de diagnóstico à baseline (ou melhorar), corrigindo o que o merge destravou ou quebrou. Verificação: differential Rust e diagnósticos iguais ou melhores que o baseline registrado.
5. **Empacotamento e performance do merge**: validar `strip`, preservação de artefatos e granularidade de seção na lane Rust; avaliar as ideias de perf C/LLVM para o runtime Rust. Verificação: binário menor, cache preservado ao trocar modo, testes de cache verdes.
6. **Cadência de sincronização**: deixar `pnpm upstream:drift` e o protocolo de merge por release documentados no plano e exercitados numa segunda sincronização de ensaio. Verificação: drift reporta 0 divergência não triada e o protocolo reproduz.

## Decisões em aberto

- **Política de conflito em `#324`/`#325`**: adotar a estrutura modular do upstream e reaplicar nossos deltas Rust (mais mergeável no futuro) ou manter nossa estrutura e portar só a mudança funcional (mais rápido agora). Recomendação: adotar a estrutura do upstream, porque a meta é sincronização contínua.
- **Merge integral de uma vez (até v0.1.4) vs por tag**: recomendação de um merge único até `upstream/main` atual, e depois um por release.
- **Escopo do Test262**: lane Rust apenas ou Rust + C/LLVM. Recomendação: Rust primário com C/LLVM como comparativo opcional.
- **Onde o merge é executado**: `main` direto (com checkpoint) ou branch `merge/upstream-20260925` e merge em `main` só depois de verde. Recomendação: branch de integração, como nas sincronizações anteriores.
