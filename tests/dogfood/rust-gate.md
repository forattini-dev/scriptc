# The Rust gate

`pnpm gate:rust` is the validation gate of this fork: the Rust lane of scriptc, judged against a committed list of known reds, so that a run finishes with a failure inventory instead of stopping at the first red. The script is `scripts/gate-rust.mjs` (plumbing) plus `scripts/gate-rust-core.mjs` (the decision rules, pinned by `tests/harness/gate-rust.test.ts`) and `scripts/gate-rust-reporter.mjs` (a streaming vitest reporter).

## What it covers

The gate runs four steps, in order, and runs every one of them even when an earlier one fails:

- `runtime-crate`: `cargo test --locked --no-fail-fast` and `cargo clippy --all-targets --locked -- -D warnings` in `packages/runtime-rust`, on the toolchain its `rust-toolchain.toml` pins (the gate sets `RUSTUP_TOOLCHAIN` to that pin for every step, so an ambient toolchain override cannot change what is being judged). `--no-fail-fast` only keeps cargo from stopping at the first failing test binary; pass or fail is unchanged from CI's `runtime_rust` job. Failing tests are reported one id each (`cargo-test::<binary>::<test>`); clippy is one id (`cargo-clippy`) with its lint count.
- `corpus`: `tests/harness/rust-differential.test.ts`, the strict full-corpus parity lane (every corpus program compiled with `backend: "rust"` and compared byte for byte against the pinned Node 24 oracle, or Node 26 or bun for `// @target` programs; the compiler and vitest run on Node 26.8.1, like CI's `node_26_host` job, and the oracle is pinned by the compat matrix rather than by the host). The corpus is split with `SCRIPTC_TEST_SHARD=i/N` (`tests/harness/shard.ts`, the same stable name hash CI uses) into N shard processes that run a few at a time, each with its own `TMPDIR`. `SCRIPTC_REQUIRE_TARGETS=1` turns a missing oracle into a red instead of a skip, `SCRIPTC_RUST_REFUSALS=1` lists refused programs in the log, and `SCRIPTC_TEST_DISCARD_PASSED_BINARIES=1` deletes the binary of every passed program so a full run does not leave tens of gigabytes behind (`--keep-binaries` keeps them).
- `focus-node26` and `focus-node24`: the focused Rust regression list that CI's `node_26_host` job runs, on Node 26.8.1 with target `node26` and then on Node 24.15.0 with target `node24`. The list is read from `.github/workflows/ci.yml` at run time, so it has one home (this work leaves `ci.yml` and CI's own `--maxWorkers=1` invocation unchanged); the gate and `tests/harness/gate-rust.test.ts` both refuse a workflow whose node26 and node24 steps name different files. Unlike CI, which hosts both steps on Node 26, each lane here runs vitest, the oracle and the target on the same interpreter (`SCRIPTC_RUNTIME_TARGET`, `SCRIPTC_NODE_ORACLE`, `SCRIPTC_NODE_NODE24`, `SCRIPTC_NODE_NODE26` are set the way the CI steps set them). Interpreters are located the way `tests/harness/node-matrix.ts` locates them (`--node26`/`--node24`, then `SCRIPTC_NODE_NODE26`/`SCRIPTC_NODE_NODE24`, the running interpreter, the mise install tree, `mise which`) and every candidate is asked its `--version`; a lane whose interpreter is missing is a problem that fails the gate, never a silent skip.

What it does not cover, deliberately:

- The C and LLVM backends and the sanitized lane: `pnpm test` and `SCRIPTC_SAN=1 pnpm test` remain the three-backend gate for synchronising with upstream. `SCRIPTC_SAN=1` skips the Rust corpus entirely (`describe.skipIf(sanitize && !rustSanitize)`), and the Rust ASan gate (`pnpm test:rust:san`) needs a dated nightly this fork does not use.
- The mission configuration itself. Only corpus programs marked `// @no-engine` compile with `allowEngine: false`; every other program may embed the island engine. The corpus lane is therefore a semantic parity gate for the Rust backend, not a proof that the no-engine consumer builds (`backend: "rust"`, `allowEngine: false`, `npmStatic: "auto"`) compile.
- CI's feature-variant clippy sweeps (`island-eval,sqlite` and `island-v8,sqlite`), the `island-v8` crate's own tests, `pnpm lint`, the compat gates and the Test262 profile.
- Everything the focused list does not name. The list is CI's hand-maintained set of Rust regression files; the gate inherits its scope and its gaps.

## How to run it

```bash
pnpm gate:rust                 # full mode: every step, 16 corpus shards
pnpm gate:rust --quick         # runtime crate, corpus shards 1 and 21 of 40, focus list on Node 26 only (about 16 minutes, mostly the focus list)
pnpm gate:rust --steps runtime-crate,corpus --shards 40 --sample 1,21   # the same without the focus list: about 2 minutes warm
pnpm gate:rust --steps corpus --shards 40 --sample 3 --jobs 1
pnpm gate:rust --dry-run       # print the plan (commands and environment deltas) without running
pnpm gate:rust --help
```

Reports go to `<cache>/scriptc/gate-rust/<timestamp>-<mode>/` (`$XDG_CACHE_HOME` or `~/.cache`; `--out <dir>` overrides; `latest` points at the newest run): `report.json` holds every step, shard, test id, duration, first lines of every failure, the parity line and peak resident memory per shard; `summary.txt` is the text printed at the end; `runtime-crate/*.log`, `corpus/shard-NN/vitest.log` and `focus-*/vitest.log` are the raw child logs, and the `results.jsonl` next to each vitest log is the event stream the verdict was built from. Exit code 0 is a pass, 1 a fail, 2 a usage error.

The corpus step's concurrency is `--shards N` (how the corpus is partitioned, default 16) and `--jobs P` (how many shard processes run at once, default one per three cores and one per four gigabytes of memory, so 4 on a 12-core, 16 GB host). Each shard process is one vitest worker that compiles and runs one program at a time, so P is also the number of concurrent rustc processes, and the gate sets `SCRIPTC_NATIVE_HOST_WORKERS` to P (or 2 if larger) unless the environment already sets it, otherwise the host-wide native build seats would cap the gate at two concurrent builds regardless of P. More shards than jobs is intentional: a shard that is killed loses only its remaining programs, and the result stream keeps everything judged before the kill.

Shard processes share one `SCRIPTC_CACHE_DIR` (the vitest default `node_modules/.cache/scriptc-tests/cas`, or the ambient value) and therefore one cargo target directory per runtime feature set. This is the safe default and the configuration the ordinary suite already runs in with several vitest workers: cargo serialises concurrent builds of one target directory through its `.cargo-lock`, and a no-op build leaves the uplifted `libscriptc_runtime.rlib` untouched (measured on 2026-10-05: same inode, mtime and size before and after a 0.10 s no-op build, the uplifted file being a hard link of the `deps/` artifact), so a shard that links while another shard's cargo re-checks freshness reads the same bytes. The runtime rlib is not content addressed, so the one real hazard is a runtime source edit during a run, which would also affect the plain suite. `--isolate-cache` gives every shard its own cache directory for diagnosing a suspected cache interaction, at the price of a cold runtime build (and a V8 archive download for the first `// @dynamic` program) per shard. Per-shard `TMPDIR`s are isolated because corpus programs create scratch files and unix sockets under the temporary directory; they live under the ambient `TMPDIR` (or `~/.cache/scriptc/test-tmp`) with short names, because `sun_path` is limited to about one hundred bytes, and are removed after the shard finishes unless `--keep-tmp` is given.

## How the baseline works

`tests/dogfood/rust-gate-baseline.json` lists the known reds per step as `id → first line of the failure` (the reason is for humans; only the id is compared), plus a `calibration` block saying which commit, date and scope each step's entries were last rewritten from. The verdict is:

- a red whose id the baseline does not list is a NEW red and fails the gate;
- a red the baseline lists passes, and is reported as still red (with a note when its first line changed);
- a baseline entry that now passes is reported as fixed, and one whose test no longer exists is reported as stale; both are listed for removal and neither fails the gate;
- a baseline entry outside the scope of the run (a corpus shard that was not sampled, a step that was not selected) is reported as not checked and left alone;
- a shard that crashed, timed out or ended without a run-end record, a program or test that was collected but never produced a result, a file that executed no test, a lane whose interpreter is missing and a focus list that cannot be read are problems: they always fail the gate and are never written to the baseline.

`--update-baseline` rewrites the file from the run: entries in the run's scope are replaced by the run's reds, entries outside it are preserved, and the exit code is 0 when there were no problems. `--rejudge <report.json>` re-evaluates an earlier run's report against the baseline as it is now, with or without `--update-baseline`, so a long calibration run can be launched without committing to a baseline rewrite and the baseline derived from its report afterwards, and an edited baseline can be checked without recompiling anything. Corpus ids are the corpus-relative program names the harness prints (`001-hello.ts`, `3049-native-import-star-cycle/main.ts`); focus ids are `<file> > <describe> > <test>`; runtime-crate ids are `cargo-test::<binary>::<test>`, `cargo-test` (a build or harness failure with no parsable test) and `cargo-clippy`.

The committed baseline was calibrated on 2026-10-05 at commit 170c4dc2 from a quick run (runtime crate, corpus shards 1 and 21 of 40, focus list on Node 26) plus a focus-node24 run; its corpus entries therefore cover 110 of 2067 programs. The first full run will report the other shards' reds as new; that run should be `pnpm gate:rust` followed by `pnpm gate:rust --rejudge <its report.json> --update-baseline` once the inventory has been read, and the calibration block will then say `all 16 shards`.

## Measured timings

All numbers are from 2026-10-05 on the 12-core, 16 GB (18.7 GiB reported) WSL2 host, Node 26.8.1 as vitest host, Rust 1.98.0, while other agents were compiling on the same machine (load average 4 to 10 during the runs), so they are upper bounds for an idle host and the same lane varied by 50 % between runs. Unless a line says cold, `SCRIPTC_CACHE_DIR` had been populated by earlier runs of this work; the content-addressed caches (runtime builds, compiled binaries, oracle outputs) make a repeat run cheaper than a first one, and a compiler change invalidates part of them.

- `runtime-crate`: cold target directory, `cargo test` 33 s wall (283 tests, peak RSS 1.1 GB) and `cargo clippy` 14 s. Warm, through the gate: 6 to 9 s for both (`cargo test` 1 to 2 s, `cargo clippy` 5 to 8 s). Clippy exits 1 on one lint, `using chunks_exact with a constant chunk size` at `src/zlib.test.rs:30`, so the crate's own gate is already red at 170c4dc2; the baseline records it and the fix is a separate one-line change that this gate does not make.
- `corpus`, cold: the first program of a shard pays the runtime build, 25 s for the default feature set with `CARGO_BUILD_JOBS=3`; the first `// @dynamic` program pays the `island-v8` runtime build including the V8 archive download, about 80 s and 1.3 GB of target directory. A cold first run of 8 programs (shards 1 and 2 of 400) took 1m38s, 11.9 s per program, which is the cold-start tax and not a per-program cost. Warm: shard 1 of 40 through `pnpm gate:rust` is 60 programs in 1m49s wall (1m40s of test time, 1.67 s per program, peak 1.1 GB, 4 known reds); the quick sample, shards 1 and 21 in parallel, took 2m07s and then 1m58s (Σ test time 3m29s and 3m18s, peak 1.1 to 1.4 GB per shard process).
- Full-corpus extrapolation, with its error bar. The two quick runs measured 1.90 and 1.80 s per program over the same 110 programs; their spread (sd 0.65 s, p99 3.8 s, max 4.0 s) puts the bootstrap 95 % interval of the mean at 61 to 70 minutes of sequential test time for 2067 programs. Weighting the program classes by their corpus share (1878 plain, 166 `// @dynamic`, 19 `// @target bun`, 4 `// @target node26`, against 102, 7, 1 and 0 in the sample) gives 66 minutes. The 16 shards hold 108 to 151 programs, so four shard processes run about four rounds of about four minutes: 16 to 27 minutes for the corpus step at 100 to 60 % parallel scaling (the scaling is an assumption, not a measurement), plus cold runtime builds if the cache is empty (one to two minutes per feature set, more for `island-v8`) and about 8 s of vitest start-up per shard. What this cannot see: `// @dynamic` programs link V8 (2.4 s each in the 7 sampled, but that sample is tiny), a retried failure runs twice, one hanging program costs its 300 s test timeout, and host contention moved the same shard by up to 50 %. The full run replaces this estimate with a measurement.
- Expected size of the inventory. 11 of the 110 sampled programs are red (10 %, binomial 95 % interval 6 to 17 %), so the full corpus should show on the order of 100 to 350 corpus reds; the first full run will report every one that is not in the baseline as new.
- `focus-node26`, 28 files, 298 tests, 2 vitest workers: 15m44s wall on a first run and 14m13s on a repeat, 292 passed and 6 failed (the `'llvm'` rows of `native-error-call.test.ts` and `native-cjs-conditional-export.test.ts`, which need the LLVM native helper package this worktree has not built), peak 1.8 GB. The first run was dominated by three files that compile release binaries with fat LTO (`js-array-constructor.test.ts` 7m07s, `buffer-from-dynamic.test.ts` 6m35s, `class-factory-capture.test.ts` 2m45s); on the repeat they took 2m31s, 2m53s and 2m36s, which points at cold release caches on the first run but was not isolated, and the lane is bound by the sum of its files, 27 minutes of file time over two workers. `--focus-workers 4` (and `SCRIPTC_NATIVE_HOST_WORKERS` to match, which the gate does not set for this step) is the lever on an idle host; it was not measured.
- `focus-node24`, the same 28 files and 298 tests hosted on Node 24.15.0: 10m10s on its first run (run right after the Node 26 lane, load 5 to 6) and 14m18s on a repeat under load 7 to 10, 292 passed and 6 failed, the same six. CI runs both lanes with `--maxWorkers=1` inside a 20-minute job timeout; this gate uses two workers and a 90-minute per-process cap.
- `--quick` end to end: 18m01s on its first run (9 s + 2m07s + 15m44s) and 16m17s on a repeat on the committed gate (6 s + 1m58s + 14m13s), exit 0 against the committed baseline. That misses the aim of well under fifteen minutes: the focus list is 87 % of it and its cost is compile throughput at two workers, not the gate's overhead. Running the corpus sample beside the focus list would save about two minutes; more focus workers would save more but were not measured, because this host was shared. The cheap loop is `--steps runtime-crate,corpus --shards 40 --sample 1,21`, about two minutes warm.
- A full run is therefore estimated at roughly 40 to 60 minutes (crate 10 s, corpus 16 to 27 minutes, focus lanes 10 to 16 minutes each), extrapolated and not measured; the full corpus has not been run through the gate.

## Plumbing proof runs

Each of these ran on 2026-10-05 against the committed gate; the reports are not committed, the commands and outcomes are.

- `pnpm gate:rust --steps runtime-crate`: 9 s, exit 0 (`cargo test` 283 passed; `cargo clippy` 1 lint, known).
- `pnpm gate:rust --steps corpus --shards 40 --sample 1`: 1m49s, exit 0, 56 of 60 programs claimed, the 4 reds all in the baseline, the other 20 baseline entries reported as not checked.
- A throwaway failing test passed through `--steps focus-node26 --focus-file <file>` (the file was deleted afterwards): `NEW reds: focus-node26::<file> > deliberate red…`, exit 1 through `pnpm`.
- `--rejudge` of that corpus report against a copy of the baseline without one of its known reds: `NEW reds: corpus::2983-http-static-close-idle.ts`, exit 1.
- `pnpm gate:rust --steps corpus --shards 40 --sample 1 --timeout-min 1`: the shard process group was terminated after 1m00s, 30 of 60 programs reported as not run, `problems: shard 1/40: crashed (timed out after 1m00s) after 30 of 60 programs`, exit 1, baseline entries of the shard untouched.
- `pnpm gate:rust --quick`: 16m17s, exit 0, `PASS (0 new reds, 0 problems)`, 18 known reds still red, 6 baseline entries (the Node 24 lane) not checked.
- `pnpm gate:rust --steps focus-node24`: 14m18s, exit 0, 6 known reds still red.
- `tests/harness/gate-rust.test.ts`, the gate's own 24 unit tests, on Node 26.8.1 and on Node 24.15.0: 24 passed on each.
