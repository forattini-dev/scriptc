# The Rust gate

`pnpm gate:rust` is the validation gate of this fork: the Rust lane of scriptc, judged against a committed list of known reds, so that a run finishes with a failure inventory instead of stopping at the first red. The script is `scripts/gate-rust.mjs` (plumbing) plus `scripts/gate-rust-core.mjs` (the decision rules, pinned by `tests/harness/gate-rust.test.ts`), `scripts/gate-rust-reporter.mjs` (a streaming vitest reporter) and `scripts/gate-rust-lock.mjs` (the advisory lock).

## What it covers

The gate runs five steps, in order, and runs every one of them even when an earlier one fails:

- `runtime-crate`: `cargo test --locked --no-fail-fast` and `cargo clippy --all-targets --locked -- -D warnings` in `packages/runtime-rust`, on the toolchain its `rust-toolchain.toml` pins (the gate sets `RUSTUP_TOOLCHAIN` to that pin for every step, so an ambient toolchain override cannot change what is being judged). `--no-fail-fast` only keeps cargo from stopping at the first failing test binary; pass or fail is unchanged from CI's `runtime_rust` job. Failing tests are reported one id each (`cargo-test::<binary>::<test>`), a test binary that never prints its result summary is reported as crashed (`cargo-test::<binary>`), and every clippy diagnostic is its own id keyed by lint and file (`cargo-clippy::<lint>::<file>`, with `#2`, `#3` for repeats of one lint in one file), so a new lint is a new red even while another one is baselined.
- `rust-unit`: the Rust backend's own vitest files that neither the focus list nor the corpus step runs, hosted on Node 26.8.1 with the Node 24 executable as the semantic oracle (CI's Node 26 host job pairs them the same way) and the default runtime target. They are selected two ways. By name: `packages/compiler/test/emit-rust*.test.ts` and `rust-*.test.ts`, `packages/compiler/src/backend/rust/**/*.test.ts`, the npm-static family (`npm-static*.test.ts` in `packages/compiler/test`, `packages/compiler/src/frontend` and `tests/harness`, plus `npm-inferred-containers.test.ts`), `tests/harness/rust-*.test.ts`, `runtime-rust-package.test.ts`, CI's oracle-selection contract `oracle-environment.test.ts` and the gate's own `gate-rust.test.ts`. By content: every other vitest file whose source contains `backend: "rust"` or `--backend rust`, which is how the admission and no-engine suites that guard the mission's compile path (`no-engine.test.ts`, the `native-*-admission` family) are found without a hand-kept list; a new test that pins the Rust backend joins the step by itself. Subtracted: the focus list, the corpus file, and the case-sharded monster harnesses CI excludes from its file-sharded run (`RUST_UNIT_NEVER`). The lists are `RUST_UNIT_GLOBS`, `RUST_PIN_PATTERN` and `RUST_UNIT_NEVER` in `scripts/gate-rust-core.mjs`; `--dry-run` prints the resolved file list.
- `corpus`: `tests/harness/rust-differential.test.ts`, the strict full-corpus parity lane (every corpus program compiled with `backend: "rust"` and compared byte for byte against the pinned Node 24 oracle, or Node 26 or bun for `// @target` programs; the oracle is pinned by the compat matrix rather than by the host). The compiler and vitest run on Node 26.8.1 for this step, whereas CI's `tests` job hosts the same file on the `.node-version` Node 24 profile, so the gate has no Node 24-hosted corpus run. The corpus is split with `SCRIPTC_TEST_SHARD=i/N` (`tests/harness/shard.ts`, the same stable name hash CI uses) into N shard processes that run a few at a time, each with its own `TMPDIR`. `SCRIPTC_REQUIRE_TARGETS=1` turns a missing oracle into a red instead of a skip, `SCRIPTC_RUST_REFUSALS=1` lists refused programs in the log, and `SCRIPTC_TEST_DISCARD_PASSED_BINARIES=1` deletes the binary of every passed program so a full run does not leave tens of gigabytes behind (`--keep-binaries` keeps them). A full run also checks that the shards collected exactly as many programs as the corpus directory holds.
- `focus-node26` and `focus-node24`: the focused Rust regression list that CI's `node_26_host` job runs, on Node 26.8.1 with target `node26` and then on Node 24.15.0 with target `node24`. The list is read from `.github/workflows/ci.yml` at run time, so it has one home (this work leaves `ci.yml` and CI's own `--maxWorkers=1` invocation unchanged); the gate and `tests/harness/gate-rust.test.ts` both refuse a workflow whose node26 and node24 steps name different files. Unlike CI, which hosts both steps on Node 26, each lane here runs vitest, the oracle and the target on the same interpreter (`SCRIPTC_RUNTIME_TARGET`, `SCRIPTC_NODE_ORACLE`, `SCRIPTC_NODE_NODE24`, `SCRIPTC_NODE_NODE26` are set the way the CI steps set them). Interpreters are located the way `tests/harness/node-matrix.ts` locates them (`--node26`/`--node24`, then `SCRIPTC_NODE_NODE26`/`SCRIPTC_NODE_NODE24`, the running interpreter, the mise install tree, `mise which`) and every candidate is asked its `--version`; a lane whose interpreter is missing is a problem that fails the gate, never a silent skip.

What it does not cover, deliberately:

- The C and LLVM backends and the sanitized lane: `pnpm test` and `SCRIPTC_SAN=1 pnpm test` remain the three-backend gate for synchronising with upstream. `SCRIPTC_SAN=1` skips the Rust corpus entirely (`describe.skipIf(sanitize && !rustSanitize)`), and the Rust ASan gate (`pnpm test:rust:san`) needs a dated nightly this fork does not use.
- The mission configuration itself. Only corpus programs marked `// @no-engine` compile with `allowEngine: false`; every other program may embed the island engine. The corpus lane is therefore a semantic parity gate for the Rust backend, not a proof that the no-engine consumer builds (`backend: "rust"`, `allowEngine: false`, `npmStatic: "auto"`) compile.
- Most of the rest of the vitest suite. The gate runs 226 of the 434 vitest files (the 28 of the focus list, the 197 of `rust-unit` and the corpus file, as counted at the commit that adds the step; `--dry-run` prints the live lists) and not the other 208: 64 files under `tests/harness` (the C and LLVM differentials, island, fetch, server, library, npm, coverage, diagnostics and similar suites), 101 under `packages/compiler` that do not pin the Rust backend (frontend, IR and C/LLVM backend unit tests), the C runtime's 20 files in `packages/runtime/test`, the CLI's 19 in `packages/cli/test`, and 4 in the other packages. A change in any of those areas needs its own focused tests as well; that is why AGENTS.md asks for them.
- CI's feature-variant clippy sweeps (`island-eval,sqlite` and `island-v8,sqlite`), the `island-v8` crate's own tests, `pnpm lint`, the compat gates and the Test262 profile.

## How to run it

```bash
pnpm gate:rust                 # full mode: every step, 16 corpus shards
pnpm gate:rust --quick         # runtime crate, corpus shards 1 and 21 of 40, focus list on Node 26 only (about 16 minutes, mostly the focus list)
pnpm gate:rust --steps runtime-crate,corpus --shards 40 --sample 1,21   # the same without the focus list: about 2 minutes warm
pnpm gate:rust --steps rust-unit                                         # only the Rust backend's unit and emission tests
pnpm gate:rust --steps corpus --shards 40 --sample 3 --jobs 1
pnpm gate:rust --dry-run       # print the plan (commands, environment deltas, resolved file lists) without running
pnpm gate:rust --help
```

Reports go to `<cache>/scriptc/gate-rust/<timestamp>-<mode>/` (`$XDG_CACHE_HOME` or `~/.cache`; `--out <dir>` overrides; `latest` points at the newest run): `report.json` holds every step, shard, test id, duration, first lines of every failure, the parity line and peak resident memory per shard; `summary.txt` is the text printed at the end; `runtime-crate/*.log`, `corpus/shard-NN/vitest.log` and `focus-*/vitest.log` are the raw child logs, and the `results.jsonl` next to each vitest log is the event stream the verdict was built from. Exit code 0 is a pass, 1 a fail, 2 a usage error or a refusal to start.

The corpus step's concurrency is `--shards N` (how the corpus is partitioned, default 16) and `--jobs P` (how many shard processes run at once, default one per three cores and one per four gigabytes of memory, so 4 on a 12-core, 16 GB host). Each shard process is one vitest worker that compiles and runs one program at a time, so P is also the number of concurrent rustc processes, and the gate sets `SCRIPTC_NATIVE_HOST_WORKERS` to P (or 2 if larger) unless the environment already sets it, otherwise the host-wide native build seats would cap the gate at two concurrent builds regardless of P. More shards than jobs is intentional: a shard that is killed loses only its remaining programs, and the result stream keeps everything judged before the kill. The file steps (`rust-unit` and the focus lanes) are one vitest process each with `--focus-workers` workers (default 2).

Shard processes share one `SCRIPTC_CACHE_DIR` (the vitest default `node_modules/.cache/scriptc-tests/cas`, or the ambient value) and therefore one cargo target directory per runtime feature set. This is the safe default and the configuration the ordinary suite already runs in with several vitest workers: cargo serialises concurrent builds of one target directory through its `.cargo-lock`, and a no-op build leaves the uplifted `libscriptc_runtime.rlib` untouched (measured on 2026-10-05: same inode, mtime and size before and after a 0.10 s no-op build, the uplifted file being a hard link of the `deps/` artifact), so a shard that links while another shard's cargo re-checks freshness reads the same bytes. Four concurrent shards (190 programs) also ran with no concurrency artefact: no problem, nothing missing, and every red reproduced in isolation. The runtime rlib is not content addressed, so the one real hazard is a runtime source edit during a run, which would also affect the plain suite. `--isolate-cache` gives every shard its own cache directory for diagnosing a suspected cache interaction, at the price of a cold runtime build (and a V8 archive download for the first `// @dynamic` program) per shard. Per-shard `TMPDIR`s are isolated because corpus programs create scratch files and unix sockets under the temporary directory; they live under the ambient `TMPDIR` (or `~/.cache/scriptc/test-tmp`) with short names (`gr-<pid and random suffix>/s<N>`, unique per run so two runs never delete each other's), because `sun_path` is limited to about one hundred bytes, and are removed after the shard finishes unless `--keep-tmp` is given.

Only one gate runs at a time. `tests/harness/suite-lock.mjs` serialises full suite runs through an advisory pidfile in the temporary directory, but it engages only for a vitest run with no file filter, and the gate always passes files, so the gate takes the same lock file itself for the whole run (same path and record shape, so a gate and a full `pnpm test` queue behind each other). A holder that is dead is stolen from; a live one is waited for up to `--lock-wait-min` minutes (default 45) with a message every 30 seconds, after which the gate refuses to start with exit code 2, because a verdict taken on an oversubscribed host is worse than none (the full suite proceeds anyway; the gate does not). `--no-lock` or `SCRIPTC_NO_LOCK=1` skips it, as for the suite; `--dry-run` and `--rejudge` never take it. The lock lives in `$TMPDIR`, so runs with different `TMPDIR`s do not see each other. Four shards use about 8 GB of a 16 GB host plus rustc, so on a machine that must stay responsive give the gate fewer processes (`--jobs 1 --focus-workers 1`) and, if it runs under `pnpm limit`, raise the limiter's ceilings (`SCRIPTC_LIMIT_CPU`, `SCRIPTC_LIMIT_MEMORY_HIGH`, `SCRIPTC_LIMIT_MEMORY`; the defaults of half a CPU and 3 GiB are meant for a single focused test, and the gate would take hours at half a CPU): `SCRIPTC_LIMIT_CPU=200% SCRIPTC_LIMIT_MEMORY_HIGH=4G SCRIPTC_LIMIT_MEMORY=6G pnpm limit -- pnpm gate:rust --jobs 1 --focus-workers 1`. That recipe follows from the measured peaks below and has not been run.

If the gate itself is killed without a chance to clean up (SIGKILL, the out-of-memory killer), the vitest process of each running lane notices within ten seconds that the gate pid is gone and kills its own process group, so shard and focus processes do not keep compiling until their wall-clock cap; the cargo steps have no such guard and are short. SIGINT, SIGTERM and SIGHUP stop the children and still write the report.

## How the baseline works

`tests/dogfood/rust-gate-baseline.json` lists the known reds per step as `id → first line of the failure` (the reason is for humans; only the id is compared), plus a `calibration` block saying which commit, date and scope each step's entries were last rewritten from. The verdict is:

- a red whose id the baseline does not list is a NEW red and fails the gate;
- a red the baseline lists passes, and is reported as still red; if its first line changed since the baseline recorded it, the summary prints the old and the new first line under "known reds that now fail differently", because a program that regresses from a stdout mismatch to a compile refusal is still a known red by id. `--strict-reasons` makes that a problem that fails the gate;
- a baseline entry that now passes is reported as fixed, and one whose test no longer exists is reported as stale; both are listed for removal and neither fails the gate. A known red that only passes on a retry is not fixed: it is listed as flaky (every test that passed only on a retry is listed, whether or not it is baselined), stays in the baseline and is kept by `--update-baseline`;
- a baseline entry outside the scope of the run (a corpus shard that was not sampled, a step that was not selected) is reported as not checked and left alone;
- a shard that crashed, timed out or ended without a run-end record, a program or test that was collected but never produced a result, a file that executed no test, a lane whose interpreter is missing, a focus list that cannot be read, and any vitest process whose exit status the recorded results do not explain are problems: they always fail the gate and are never written to the baseline. The last rule is what stops a failure the test records do not show from passing: vitest exiting 1 with no failed test, suite hook error, module error or unhandled error recorded, or a module that ended in state `failed` for no recorded reason, is a problem; a vitest exit of 0 with failures recorded is one too.

A failing `beforeAll` or `afterAll` in a describe, which leaves every test of the file passed or skipped, is reported by the reporter as a suite-level record and judged as a red keyed `<file> > <suite> [suite hook failed]`; a module-level error (an import that throws, a module-level hook) is a red keyed by the file. In the corpus step either one is a problem instead, because the corpus file has no hooks that should fail.

`--update-baseline` rewrites the file from the run: entries in the run's scope are replaced by the run's reds, entries outside it are preserved, and the exit code is 0 when there were no problems. `--rejudge <report.json>` re-evaluates an earlier run's report against the baseline as it is now, with or without `--update-baseline`, so a long calibration run can be launched without committing to a baseline rewrite and the baseline derived from its report afterwards, and an edited baseline can be checked without recompiling anything. Corpus ids are the corpus-relative program names the harness prints (`001-hello.ts`, `3049-native-import-star-cycle/main.ts`); file-step ids are `<file> > <describe> > <test>`; runtime-crate ids are `cargo-test::<binary>::<test>`, `cargo-test::<binary>` (a crashed binary), `cargo-test` (a build or harness failure no test explains), `cargo-clippy::<lint>::<file>[#n]` and `cargo-clippy` (clippy failed without a parsable diagnostic).

A baseline is calibrated on one host. The six `'llvm'` rows of each focus lane and 28 of the `rust-unit` entries (with a few `llvm`-variant knock-ons of the same) are red only where the LLVM native helper package has not been built (`@scriptc/llvm-<platform>`, `pnpm --filter @scriptc/llvm-<platform> build:native`; this worktree has not built it), and their reason text says so. On a host that has built it they pass and are reported as fixed, which does not fail the gate; if one of them fails there for a real reason, its first line differs from the recorded one, which the summary lists under "known reds that now fail differently" and `--strict-reasons` turns into a failure. One `rust-unit` entry is a 120 s test timeout, which depends on host load and may pass on an idle host (it would then show up as fixed), and one is a release-binary size ceiling (214037 bytes against 200000), which depends on the toolchain rather than the load.

The committed baseline was calibrated on 2026-10-05 against the compiler and runtime state of commit 170c4dc2 (nothing under `packages/` or `tests/corpus/` has changed since, and the `commit` in each calibration entry names that state, not the commit that carries the gate): `runtime-crate`, `focus-node26` and `focus-node24` in full, `rust-unit` in full from one 195-file run (`pnpm gate:rust --steps rust-unit`, then `--rejudge <report.json> --update-baseline`, with the one red the fix of `af2b598a` removed), and `corpus` for shards 1 and 21 of 40 only, 110 of 2067 programs. The first full run will therefore report the other corpus shards' reds as new, so "no new reds" is not a bar anyone can meet until that run has been done and its baseline committed: run `pnpm gate:rust`, read the inventory, then `pnpm gate:rust --rejudge <its report.json> --update-baseline`, and the calibration block will say `all 16 shards`. The AGENTS.md proposal should be merged only after that.

## Measured timings

All numbers are from 2026-10-05 on the 12-core, 16 GB (18.7 GiB reported) WSL2 host, Node 26.8.1 as vitest host, Rust 1.98.0, while other agents were compiling on the same machine (load average 4 to 10 during the runs), so they are upper bounds for an idle host and the same lane varied by 50 % between runs. Unless a line says cold, `SCRIPTC_CACHE_DIR` had been populated by earlier runs of this work; the content-addressed caches (runtime builds, compiled binaries, oracle outputs) make a repeat run cheaper than a first one, and a compiler change invalidates part of them.

- `runtime-crate`: warm, through the gate, 7 s to 25 s depending on host load (`cargo test` 1 to 15 s for 283 tests, `cargo clippy` 6 to 10 s); cold target directory, `cargo test` 33 s wall (peak RSS 1.1 GB) and `cargo clippy` 14 s. Clippy exits 1 on one lint, `clippy::chunks-exact-to-as-chunks` at `src/zlib.test.rs:30`, so the crate's own gate is already red at 170c4dc2; the baseline records it (`cargo-clippy::clippy::chunks-exact-to-as-chunks::src/zlib.test.rs`) and the fix is a separate one-line change that this gate does not make.
- `rust-unit`, 195 files at the time of the run (197 now, the two added files being the gate's own lock and reporter tests, which are green and baseline nothing), 1163 tests, 2 vitest workers: 50m55s wall (3048 s) on a host with load 3 to 11, peak 2.1 GiB, Σ file time 93.8 minutes, 56 failed of which 55 are in the baseline (the 56th was a test of the gate's own dry-run plan that depended on the ambient environment, fixed in `af2b598a` and not baselined), 0 skipped, 0 flaky. It is the longest step of the gate: five files hold 38 % of the file time (`emit-rust.test.ts` 16.6 minutes for its 108 tests, `npm-static.test.ts` 7.4, `emit-rust-record-order.test.ts` 4.1, `emit-rust-island-modules.test.ts` 3.8, `bun-island-trap.test.ts` 3.6). `--focus-workers 4` (which this lane shares) is the lever on an idle host and was not measured; CI splits `emit-rust.test.ts` ten ways with `SCRIPTC_TEST_SHARD`, which this lane does not do. 28 of the 55 baselined reds fail because the LLVM native helper package is not built in this worktree, and four more are `llvm`-variant knock-ons of it.
- `corpus`, cold: the first program of a shard pays the runtime build, 25 s for the default feature set with `CARGO_BUILD_JOBS=3`; the first `// @dynamic` program pays the `island-v8` runtime build including the V8 archive download, about 80 s and 1.3 GB of target directory. A cold first run of 8 programs (shards 1 and 2 of 400) took 1m38s, 11.9 s per program, which is the cold-start tax and not a per-program cost. Warm: shard 1 of 40 through `pnpm gate:rust` is 60 programs in 1m49s wall (1m40s of test time, 1.67 s per program, peak 1.1 GB, 4 known reds); the quick sample, shards 1 and 21 in parallel, took 2m07s and then 1m58s (Σ test time 3m29s and 3m18s, peak 1.1 to 1.4 GB per shard process). In this round's final proof run, shard 1 of 40 through the final gate took 2m44s at a load of about 10 (2.55 s per program, 1.5 GB peak, the same 4 known reds), which is what a shared host does to the same shard.
- Full-corpus extrapolation, with its error bar. The two quick runs measured 1.90 and 1.80 s per program over the same 110 programs; their spread (sd 0.65 s, p99 3.8 s, max 4.0 s) puts the bootstrap 95 % interval of the mean at 61 to 70 minutes of sequential test time for 2067 programs. Weighting the program classes by their corpus share (1878 plain, 166 `// @dynamic`, 19 `// @target bun`, 4 `// @target node26`, against 102, 7, 1 and 0 in the sample) gives 66 minutes. The 16 shards hold 108 to 151 programs, so four shard processes run about four rounds of about four minutes: 16 to 27 minutes for the corpus step at 100 to 60 % parallel scaling (the scaling is an assumption, not a measurement), plus cold runtime builds if the cache is empty (one to two minutes per feature set, more for `island-v8`) and about 8 s of vitest start-up per shard. What this cannot see: `// @dynamic` programs link V8 (2.4 s each in the 7 sampled, but that sample is tiny), a retried failure runs twice, one hanging program costs its 300 s test timeout, and host contention moved the same shard by up to 50 %. The full run replaces this estimate with a measurement.
- Expected size of the inventory. 11 of the 110 sampled programs are red (10 %, binomial 95 % interval 6 to 17 %), so the full corpus should show on the order of 100 to 350 corpus reds; the first full run will report every one that is not in the baseline as new.
- `focus-node26`, 28 files, 298 tests, 2 vitest workers: 15m44s wall on a first run and 14m13s on a repeat, 292 passed and 6 failed (the `'llvm'` rows of `native-error-call.test.ts` and `native-cjs-conditional-export.test.ts`, which need the LLVM native helper package this worktree has not built), peak 1.8 GB. The first run was dominated by three files that compile release binaries with fat LTO (`js-array-constructor.test.ts` 7m07s, `buffer-from-dynamic.test.ts` 6m35s, `class-factory-capture.test.ts` 2m45s); on the repeat they took 2m31s, 2m53s and 2m36s, which points at cold release caches on the first run but was not isolated, and the lane is bound by the sum of its files, 27 minutes of file time over two workers. `--focus-workers 4` (and `SCRIPTC_NATIVE_HOST_WORKERS` to match, which the gate does not set for this step) is the lever on an idle host; it was not measured.
- `focus-node24`, the same 28 files and 298 tests hosted on Node 24.15.0: 10m10s on its first run (run right after the Node 26 lane, load 5 to 6) and 14m18s on a repeat under load 7 to 10, 292 passed and 6 failed, the same six. CI runs both lanes with `--maxWorkers=1` inside a 20-minute job timeout; this gate uses two workers and a 90-minute per-process cap.
- `--quick` end to end (the committed gate of round 1; the final measurement of this round follows): 18m01s on its first run (9 s + 2m07s + 15m44s) and 16m17s on a repeat on the committed gate (6 s + 1m58s + 14m13s), exit 0 against the committed baseline. That misses the aim of well under fifteen minutes: the focus list is 87 % of it and its cost is compile throughput at two workers, not the gate's overhead. Running the corpus sample beside the focus list would save about two minutes; more focus workers would save more but were not measured, because this host was shared. The cheap loop is `--steps runtime-crate,corpus --shards 40 --sample 1,21`, about two minutes warm.
- `--quick`, final measurement of this round (`pnpm gate:rust --quick` with the final gate code, load average 7 to 9): 21m12s end to end (21 s + 2m25s + 18m26s), exit 0, `PASS (0 new reds, 0 problems)`, 18 known reds still red and none of them failing differently. It is the slowest of the three quick measurements (18m01s, 16m17s, 21m12s) and tracks the host load rather than the gate: the focus lane took 18m26s against 14m13s for the same 28 files and 298 tests under a lighter load. The aim of well under fifteen minutes is still missed; `--focus-workers` is the lever and `rust-unit` is already outside `--quick`.
- A full run is therefore estimated at roughly 95 to 120 minutes: `runtime-crate` 10 to 25 s, `rust-unit` about 51 minutes, the corpus 16 to 37 minutes (the lower figure from the idle-host per-program time, the upper from the 2.55 s per program just quoted), and the two focus lanes about 14 minutes each. The `rust-unit` figure is measured; the rest is extrapolated and the full corpus has not been run through the gate. Everything the gate does can be narrowed with `--steps` and `--skip`, and `--quick` leaves `rust-unit` and the Node 24 focus lane out.
