# Redwall requalification (2026-10-05)

This note answers one question with measurements, not fixes: does the current compiler still compile the committed redwall renderer as engine-free Rust, and what does the renderer look like under the mission configuration (`backend: rust`, `allowEngine: false`, `npmStatic: auto`, release optimization, targets `bun`, `node26` and `node24`)? The consumer was never edited; every measurement ran against a fresh clone of red-dev at its recorded remote main, and the compiler ran from source in the worktree `dogfood/redwall-requalify` at commit 170c4dc2. The compact machine-readable record is `redwall-requalification-2026-10-05.evidence.json` next to this file; large artifacts stay under the mission scratch directory it names.

## Answer in one paragraph

No. The committed renderer, byte-identical to the sources qualified on 2026-09-10, is refused by the current compiler with three `SC2020` diagnostics on every target, all three are compiler regressions introduced between 2026-09-14 and 2026-09-26, and a first-parent bisect over source snapshots names the commit for each. Nothing else in the renderer is a blocker: a scratch copy with only those three expressions rewritten lowers with zero diagnostics and zero runtime fences, builds in about one minute for each target, passes all 38 consumer contracts pixel for pixel, and its PNGs are byte-identical to Node 26.8.1 and Node 24.15.0. The September compiler, extracted as a source snapshot, still builds the unmodified renderer on this machine and still passes the 38 contracts byte for byte under Bun 1.4.2, so the environment is not what changed. The one target-specific gap is the deflate byte stream: the September runtime's level 9 matched Bun and not Node, and the current runtime's default level matches Node and not Bun.

## Three regressions since 2026-09-10

Each regression has a minimal reproduction that prints the same line under Node 26.8.1, Node 24.15.0 and Bun 1.4.2 and is refused with exactly one `SC2020` by the current compiler on targets `node26` and `bun`. The bisect extracted `packages/compiler` at each candidate commit with `git archive` into scratch (no branch, worktree or ref), pointed it at the worktree's `node_modules`, and ran analysis on the reproduction; it walked the 132 first-parent commits between aa57877e and HEAD. The September snapshot aa57877e analyzes all three reproductions and the full renderer with zero diagnostics.

### A. `deflateSync` with an options object

```ts
import { deflateSync, inflateSync } from "node:zlib";
const data = new Uint8Array(4096);
for (let i = 0; i < data.length; i++) data[i] = (i * 31 + (i >> 3)) & 255;
const packed = deflateSync(data, { level: 9 });
const back = inflateSync(packed);
console.log(packed.length, back.length, back[17], back[4095]);
```

Last good 3be65552 (2026-09-26 22:09 -03), first bad d3036197 `feat(rust): lower zlib callbacks and crc32` (2026-09-26 22:39 -03). That commit added `if (bi.module === "zlib") return lowerZlibModuleCall(...)` at the top of `lowerBuiltinModuleCall` (`packages/compiler/src/frontend/lowering/lower-builtins.ts:1100`); `lowerZlibModuleCall` refuses any one-shot call with more than one argument. The level-aware path `lowerDeflateLevel` (`lower-zlib.ts:12`, `{ level: -1 | 0 | 9 }` through the `zlib.deflateSyncLevel` libcall, added by e7bcadbc on 2026-09-07) is still dispatched at `lower-builtins.ts:1861`, but that line is now unreachable. The runtime libcall, its validator row and both backends still exist. The existing corpus program `tests/corpus/3144-zlib-compression-views.ts` exercises `{ level: 0 }` and `{ level: 9 }` and fails in the strict Rust lane today with this exact diagnostic.

### B. `TypedArray.set` from a numeric tuple or `number[]`

```ts
const SIGNATURE = [0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a] as const;
const out = new Uint8Array(12);
out.set(SIGNATURE, 0);
console.log(out.join(","));
```

Last good 00501b5a (2026-09-26 18:41 -03), first bad a96cb8ad `fix: restore native bigint backends` (2026-09-26 19:01 -03). That commit switched `lowerer.ts:111` to import `lowerBytesMethodCall` from `./containers/bytes.js`, the module introduced by the upstream refactor 2bd2e6f5 (#325); its `.set` path is `bytes-set.ts` `lowerSameKindBytesSetCall`, which admits only same-kind typed-array sources (plus, since c255af20, an optional union of them). The fork's tuple- and `number[]`-capable `lowerBytesSetCall` (`lower-native-containers.ts`, e7bcadbc) is still dispatched from the older copy of `lowerBytesMethodCall` in `lower-containers.ts:5946`, but nothing imports that copy any more. `tests/corpus/3001-typed-array-set-sources.ts` covers tuple and `number[]` sources and fails in the strict Rust lane today with six `SC2020` of this family.

### C. `Number.isSafeInteger` on a narrowed `number | null | undefined`

```ts
function validCount(value: number | null | undefined): value is number {
  return value !== null && value !== undefined && Number.isSafeInteger(value) && value >= 0;
}
const samples: (number | null | undefined)[] = [3, 0, -1, 1.5, null, undefined, 2 ** 53];
console.log(samples.map((value) => validCount(value)).join(","));
```

Last good b659bd0d (2026-09-14 09:34 -03), first bad 54f08faf `merge: upstream v0.1.1 compiler updates while preserving the Rust native lane` (2026-09-14 17:56 -03), which brought in upstream 94fd361b `Implement sparse native arrays and missing-value parity (#297)`. That change replaced `L.lowerExpr(argNode)` in `lowerNumberStaticCall` with `lowerBuiltinValuePreservingUndefined` (`lower-builtins.ts:138-142`, call at `:7595`), whose first choice `runtimeOptionalIdentifierValue(node)` yields the identifier's declared `number | null | undefined` instead of the checker's narrowed `number`; `lowerOptionalNumberPredicate` only handles the two-arm `number | undefined` shape, so the three-arm union reaches the non-`f64` refusal. The corpus has no coverage of this shape (`tests/corpus/1420-number-statics.ts` passes; it uses literal arguments). This is the oldest of the three: the renderer stopped compiling on 2026-09-14, four days after the last qualification.

Focused lane run: `SCRIPTC_NODE_ORACLE=$NODE24 vitest run tests/harness/rust-differential.test.ts -t '3144-zlib-compression-views|3001-typed-array-set-sources|1420-number-statics' --maxWorkers=2` on Node 26.8.1 as host and Node 24.15.0 as oracle: 1 passed (1420), 2 failed (3001, 3144), 2064 skipped, 36.5 s. The strict Rust lane has not completed since 2026-09-30, which is how both regressions stayed invisible.

## Behind the three refusals: a diagnostic variant

To measure what the current compiler does with the rest of the renderer, a second scratch clone at the same commit received exactly three rewrites, recorded as `$MISSION_SCRATCH/variant.patch` (also embedded in the evidence JSON): `deflateSync(filtered(...))` without the options object, a `for` loop in place of `out.set(SIGNATURE, 0)`, and an early return plus a `const count: number = value` binding in `validCount`. This is a measuring device, not a qualification: the consumer must not be bent to the compiler, and the first rewrite changes the compressed bytes.

## Environment: the October probes and two `@types/node` majors

The audit's finding F8 said, without executing it, that the `Property 'on' does not exist on type 'ChildProcess'` errors in the October probes come from two `@types/node` majors in one checker program. Executed here with the clean clone:

| Program | Ancestor `@types/node` of the wrapper | Consumer reached | Result |
| --- | --- | --- | --- |
| wrapper + sibling module calling `child.on("exit")` + renderer import | 24.13.3 (worktree) | yes, its `types: ["bun-types"]` reaches 26.1.2 | preflight failed: `Property 'on' does not exist on type 'ChildProcessWithoutNullStreams'` plus one implicit-any cascade |
| same wrapper without the renderer import | 24.13.3 | no | preflight passed, 4 statements, 0 diagnostics |
| same wrapper, ancestor symlinked to the consumer's 26.1.2 | 26.1.2 | yes | preflight passed; only the three known SC2020 remain |
| renderer import alone (the committed closure has no `ChildProcess.on` call) | 24.13.3 | yes | preflight passed; only the three known SC2020 remain |

So F8 holds: mixing 24.13.3 and 26.1.2 in one program removes the EventEmitter members of `ChildProcess`, and the same version reached twice does not. For the October redwall probes this is an environment problem twice over: the wrapper sat inside the scriptc repository next to its own `types: ["node"]` tsconfig, and it imported the dirty working tree, whose uncommitted `runtime-compat.ts` and `ui.ts` are what call `.on`. The committed renderer has no such call, so an adapter outside the repository never sees the error. The compiler-side root (per-tsconfig type closures unioned without reconciling majors) is real but belongs to another workstream; the three files above are its minimal reproduction.

## Reproducing

1. Clone and install: `git clone --no-hardlinks --no-checkout /home/cyber/workspace/red-dev red-dev-clean && cd red-dev-clean && git fetch origin refs/remotes/origin/main && git checkout --detach FETCH_HEAD && bun install --frozen-lockfile` (HEAD must be 9cbdcdf6).
2. Adapter: `node scripts/prepare-native-redwall.mjs --consumer <clone> --out <dir> [--theme obsidian]`, then `node <dir>/fixture.ts` (or `bun`) to write `input.json`. The script now takes `--theme` and also writes `differential.mjs`; everything else is unchanged.
3. Build: the repository's receipt path is `pnpm build && node scripts/native-acceptance.mjs --entry <dir>/main.ts --out <dir>/native --target node26 --cwd <clone> -- bun test --timeout 60000 --preload <dir>/preload.ts src/redwall-render.test.ts`; it imports `packages/compiler/dist`, so `pnpm build` is required (the CLI from source has the same requirement, which is why this run used a small tsx driver over `packages/compiler/src`; the driver is embedded in the evidence JSON). Two caveats: `native-acceptance.mjs --npm-static` forwards its values as a package list, so the literal `auto` of the mission configuration cannot be requested through it today (the renderer closure imports no npm package, so the omission changes nothing for this entry), and until regressions A to C are fixed the analysis stops with the three diagnostics above.
4. Contracts (Bun oracle): `SCRIPTC_NATIVE_REDWALL_BINARY=<binary> bun test --timeout 60000 --preload <dir>/preload.ts src/redwall-render.test.ts` from the clone.
5. Differential (Node or Bun oracle): `node <dir>/differential.mjs --binary <binary> --input <dir>/input.json --out <results> --oracle /path/to/node` (or `--oracle bun`); it exits non-zero unless status, stdout, stderr, PNG bytes and raster all match and writes `differential.json` with each side's hashes and the differing-pixel count. Run it under Node 26.8.1 and Node 24.15.0; both were exercised here.

## Limitations and what was not done

- The variant numbers describe a three-line rewrite of the consumer, not the committed renderer; they bound the distance behind the refusals and nothing more.
- No full test lane ran; only the three-program focused Rust lane above. The regressions therefore have focused evidence, not gate evidence.
- The September snapshot ran against the current `node_modules` (TypeScript 7.0.2 in both) and rustc 1.98.0 instead of 1.97.1; the generated Rust was nevertheless byte-identical to the receipt.
- Timings are single runs on a shared 12-core machine with other agents compiling; none of them is a benchmark.
- No compiler change was made. The three regressions, the dual-majors frontend gap and the two deflate byte-stream mismatches are handed over as measured.
