# Native async suspension

The Rust-native frontend lowers `async` functions without suspension, a restricted terminal `return await` in a straight-line function body, and concise async arrows whose body is `await` on a matching Promise. It also supports a straight-line async body that initializes a number or string local from `await`, optionally writes to the console or assigns represented locals and record fields, and returns a simple arithmetic or string expression using supported bindings, object fields and literals. Captured locals and objects live in traced continuation frames; boxed mutable bindings retain their shared cells, and module globals are read when the continuation runs. These forms register a native Promise reaction and resume through the microtask queue. Other `await` positions are refused. A rejected or pending promise must not be turned into a blocking Rust call: JavaScript resumes the continuation in a later microtask, after the current execution returns to the event loop.

The shared IR defines `awaitExpr` and `awaitUnionExpr`; the native IR currently represents and validates `awaitExpr` for a Promise operand. The Rust backend supports the restricted cases above; other shapes require extending the owned continuation frames to preserve local values, references, evaluation order, receiver identity, and the active completion state across suspension. An exception delivered on resumption must enter the original `catch` and `finally` regions; a return or throw in a finalizer must replace the pending completion according to JavaScript rules. Continuation frames and their captured values must participate in cycle collection.

Top-level await also requires module evaluation to track completion per module. Dependencies must finish before dependent module bodies execute, while independent work and promise reactions retain their specified ordering. Flattening all modules into a single synchronous entry function cannot express that contract. A terminal expression such as `process.exit(await run())` is one acceptance case, not a substitute for module sequencing or general async functions.

Implementation should proceed from the shared IR and validator, through a minimal resumable function and runtime continuation ownership, to nested expressions, branches, loops, protected regions, and finally module evaluation. Each step needs Node differential tests for fulfilled and rejected promises, already-settled and pending promises, observable microtask ordering, captures and collection; unsupported forms must remain explicit refusals until their continuation is implemented. The redDB builds remain integration tests rather than proof of complete async semantics.
